# نقشه راه جامع مدیریت دانش تایلندگرد
## Knowledge Master Plan

**نسخه:** ۱.۰ (پیش‌نویس هماهنگ‌کننده)
**تاریخ:** ۲۳ مهر ۱۴۰۵
**وضعیت:** در انتظار خروجی تیم‌های ۱ تا ۹ — این سند قرارداد یکپارچه‌سازی است.

---

## ۱. چشم‌انداز

هر یک از ۱۵ تیم تایلندگرد یک «ساب‌ایجنت دانش» دارد که در شروع نوبت تیم:
۱. منابع معتبر آموزشی و دانشی را می‌خواند
۲. نکات جدید را استخراج می‌کند
۳. در دانش جمعی همان تیم ذخیره می‌کند

دانش، دارایی اصلی تیم‌هاست نه محصول جانبی. این سند نقشه راه پیاده‌سازی است.

## ۲. وضعیت موجود (نقطه شروع)

زیرساخت فعلی که باید حفظ و گسترش یابد:

| مؤلفه | فایل/جدول | وضعیت |
|---|---|---|

| چانک‌های RAG | `knowledge_chunks` (vector 1536, knowledge_id) | موجود |
| دسته‌بندی دانش | `knowledge_categories` | موجود |
| حافظه تیم | `team_memory` | موجود |
| بازیابی دانش | `lib/rag.ts` (retrieveKnowledge, buildKnowledgePromptSection) | موجود |
| ایندکس دانش | `indexKnowledge`, `deleteKnowledgeIndex` در `lib/rag.ts` | موجود |
| امتیازدهی دانش | `lib/teams/knowledge.ts` (evaluateTeamKnowledge) + `lib/knowledge-score.ts` | موجود |
| API مدیریت دانش | `POST /api/manager/knowledge` | موجود |

**قراردادهای موجود که نباید شکسته شوند:**
- `indexKnowledge` قبل از ذخیره، رکورد والد در `team_knowledge` می‌خواهد و `source` اجباری است.
- شناسه دانش باید UUID معتبر باشد.
- دانش در پرامپت سرپرست تیم‌ها از طریق `knowledgeSection` تزریق می‌شود.

## ۳. تقسیم کار ۹ تیم

### تیم ۱: اسکیمای دیتابیس
**خروجی:** مایگریشن SQL + مستند اسکیما در `docs/knowledge-schema.md`

جدول‌های جدید (پیشنهاد اولیه، قابل بازبینی توسط تیم ۱):

```sql
-- منابع دانش هر تیم
knowledge_sources (
  id UUID PRIMARY KEY,
  team TEXT NOT NULL,                    -- نام تیم (۱۵ تیم)
  url TEXT NOT NULL,
  title TEXT,
  source_type TEXT NOT NULL,             -- 'official_docs' | 'expert_blog' | 'research' | 'competitor' | 'course'
  authority_tier INT NOT NULL DEFAULT 3, -- ۱ (بالاترین) تا ۳
  fetch_frequency_days INT DEFAULT 30,
  last_fetched_at TIMESTAMPTZ,
  is_active BOOLEAN DEFAULT true,
  created_at TIMESTAMPTZ DEFAULT now()
);

-- متادیتای غنی دانش (گسترش team_knowledge موجود، نه جایگزینی)
-- پیشنهاد: ستون‌های جدید روی team_knowledge
ALTER TABLE team_knowledge ADD COLUMN IF NOT EXISTS
  authority_tier INT DEFAULT 3,
  fetched_at TIMESTAMPTZ,
  relevance_score FLOAT,
  shared_with_teams TEXT[] DEFAULT '{}',  -- تیم‌های دیگری که این دانش به دردشان می‌خورد
  expires_at TIMESTAMPTZ,                 -- برای دانش تاریخ‌دار
  origin TEXT DEFAULT 'manual';           -- 'manual' | 'knowledge_subagent' | 'critic_feedback' | 'shared'
```

**قرارداد برای تیم‌های دیگر:** نام جدول‌ها و ستون‌ها دقیقاً همین باشد. اگر تیم ۱ تغییری داد، باید در `docs/knowledge-schema.md` ثبت و به هماهنگ‌کننده اعلام کند.

### تیم ۲: معماری ساب‌ایجنت دانش
**خروجی:** `docs/knowledge-subagent-design.md` + پیاده‌سازی اولیه در `lib/knowledge-subagent.ts`

- ساب‌ایجنت در **شروع** نوبت تیم اجرا می‌شود (قبل از سرپرست)، نه وسط کار.
- ورودی: فهرست منابع فعال تیم از `knowledge_sources` + دانش‌های نیازمند بازخوانی.
- خروجی: حداکثر ۵ نکته جدید در هر نوبت (سقف هزینه).
- ثبت در `subagents` با label مشخص (مثل `دانش: خوانش منابع`) تا در UI دیده شود.
- خطا در ساب‌ایجنت دانش **نباید** تیم اصلی را متوقف کند (best-effort).

### تیم ۳: خط لوله دریافت و استخراج
**خروجی:** `docs/knowledge-pipeline.md` + توابع در `lib/knowledge-pipeline.ts`

مراحل:
```
fetch (دریافت URL) → extract (استخراج نکات با LLM) → dedupe (حذف تکراری با شباهت برداری)
  → validate (فیلتر کیفیت) → store (ذخیره + ایندکس RAG)
```

- `dedupe`: شباهت کسینوسی بالای ۰.۹۲ با دانش موجود = تکراری، ذخیره نمی‌شود.
- `validate`: حداقل طول، عدم تبلیغاتی بودن، مرتبط بودن با مأموریت تیم.
- هر مرحله لاگ می‌شود تا قابل اشکال‌زدایی باشد.

### تیم ۴: تعمیم نقد←دانش به ۱۵ تیم
**خروجی:** تابع مشترک در `lib/critic-to-knowledge.ts` + حذف کد اختصاصی branding

- الگوی فعلی `lib/teams/branding.ts` (استخراج حکم منتقد) به تابع عمومی تبدیل شود.
- ساختار دانش ذخیره‌شده: `{ الگوی مردود، دلیل، دامنه، قاعده آینده، شاهد }`.
- در پایان هر تیم، اگر `verdict.approved === false` یا نقد نکته‌ای داشت، خودکار به دانش تبدیل شود.
- ثبت موفق/ناموفق در لاگ (نه بلعیدن بی‌صدا).

### تیم ۵: سیستم تازگی و امتیازدهی
**خروجی:** گسترش `lib/teams/knowledge.ts` + `docs/knowledge-freshness.md`

- دانش با سن بیش از ۳۰ روز: پرچم «نیازمند بازخوانی».
- دانش با سن بیش از ۱۲۰ روز: امتیاز تازگی صفر، در اولویت بازخوانی ساب‌ایجنت.
- `expires_at` برای دانش تاریخ‌دار (مثل قیمت‌ها، قوانین) — پس از انقضا آرشیو می‌شود نه حذف.
- امتیاز تیم در صفحه دانش داشبورد نمایش داده شود.

### تیم ۶: اشتراک‌گذاری بین‌تیمی
**خروجی:** `docs/knowledge-sharing.md` + منطق تگ‌گذاری

- هنگام ذخیره دانش، LLM تیم‌های مرتبط را پیشنهاد می‌دهد (حداکثر ۳ تیم).
- دانش مشترک در `buildKnowledgePromptSection` تیم‌های مقصد هم تزریق می‌شود.
- قانون: دانش مشترک فقط خواندنی است؛ ویرایش فقط توسط تیم مالک.

### تیم ۷: UI داشبورد
**خروجی:** صفحه‌ها و کامپوننت‌ها (وایب‌فارسی، فارسی، موبایل‌فرست)

- صفحه «منابع دانش» برای هر تیم: افزودن/ویرایش/حذف/فعال‌سازی منبع + درجه اعتبار.
- نمایش امتیاز دانش هر تیم (از `evaluateTeamKnowledge`).
- نمایش دانش‌های اخیر + منشأ (دستی/ساب‌ایجنت/نقد/مشترک).
- دکمه «خوانش اکنون» برای اجرای دستی ساب‌ایجنت دانش.

### تیم ۸: APIهای مدیریت دانش
**خروجی:** اندپوینت‌های `app/api/manager/knowledge/*`

- `GET/POST /api/manager/knowledge/sources` — مدیریت منابع.
- `POST /api/manager/knowledge/sources/[id]/fetch` — خوانش دستی.
- `GET /api/manager/knowledge/evaluation/[team]` — امتیاز تیم.
- همه با احراز مدیر (الگوی موجود `requireManagerAuth`).

### تیم ۹: تست و معیارهای کیفیت
**خروجی:** `docs/knowledge-quality-metrics.md` + تست‌های خودکار

- تست dedupe: دو متن مشابه → فقط یکی ذخیره شود.
- تست تزریق: دانش ذخیره‌شده در پرامپت تیم بعدی ظاهر شود.
- تست نقد←دانش: verdict ردشده → رکورد دانش ساخته شود.
- معیارها: بخش ۶ همین سند.

## ۹. دفتر ناسازگاری‌ها و تصمیم‌های هماهنگ‌کننده

### ناسازگاری ۱: برچسب منبع دانش منتقد — اصلاح شد
- **سند خط لوله** فرض کرده درس‌های منتقد با `source = 'team-lesson'` ذخیره می‌شوند.
- **واقعیت کد** (`lib/knowledge/critic-knowledge.ts:68`): مقدار واقعی `'critic-verdict'` است.
- **تصمیم:** همه اسناد از این پس از `critic-verdict` استفاده کنند. پیشنهاد تیم ۳ برای چانک‌های ساب‌ایجنت (`knowledge-source`) پذیرفته شد؛ پس سه مقدار مجاز `source`: `critic-verdict` | `knowledge-source` | `manual`.

### ناسازگاری ۲: مسیر API منابع — تصمیم گرفته شد
- **سند UI** پیشنهاد داده: `/api/knowledge/sources/*`.
- **واقعیت:** API موجود دانش در `/api/manager/knowledge` است و همه با `requireManagerAuth` محافظت می‌شوند.
- **تصمیم:** مسیر نهایی `/api/manager/knowledge/sources/*` است (سازگار با قرارداد احراز موجود). تیم ۸ و تیم ۷ (UI) مسیرها را همین بگذارند.

### ناسازگاری ۳: نام فیلدهای جدول منابع — به تیم ۱ ارجاع شد
- **سند UI** انتظار دارد: `name`, `type`, `authority`, `refresh_interval` (رشته: daily/weekly/monthly/manual), `last_test_ok`, `records_count`.
- **پیشنهاد اولیه این سند:** `fetch_frequency_days` (عدد)، `authority_tier`، `source_type`.
