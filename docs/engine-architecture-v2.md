| نقش | تکنولوژی | دلیل |

## ۲. استدلال فنی: چرا گیت‌هاب اکشنز می‌ماند

### ۲.۱. محدودیت زمانی سرورلس

یک تیم تایلندگرد در هر اجرا ده‌ها فراخوانی LLM می‌زند. زمان واقعی اجرا:

| تیم | فراخوانی LLM تقریبی | زمان تقریبی |
|---|---|---|
| artdir | ۳ تا ۱۰ | ۲ تا ۸ دقیقه |
| content | ۵ تا ۱۵ | ۵ تا ۱۵ دقیقه |
| dev | ۱۰ تا ۳۰ | ۱۰ تا ۲۵ دقیقه |

محدودیت ورسل (پلن Hobby): تابع سرورلس حداکثر ۶۰ ثانیه. حتی با `waitUntil`، سقف سخت‌افزاری پابرجاست و تابع کشته می‌شود. این در پروداکشن ثابت شد: موج‌ها نصفه می‌ماندند و چرخه گیر می‌کرد.

گیت‌هاب اکشنز: ۳۰ دقیقه برای هر job. یک تیم کاملاً جا می‌شود.

### ۲.۲. محیط اجرا

| نیاز | ورسل سرورلس | گیت‌هاب اکشنز |
|---|---|---|
| Node.js کامل | محدود | کامل |
| npm install | نه | بله (`npm ci`) |
| فایل‌سیستم قابل نوشتن | موقت و محدود | کامل |
| لاگ بلندمدت | محدود | کامل (۹۰ روز) |

### ۲.۳. چرا زمان‌بند ورسل می‌ماند (نه schedule گیت‌هاب)

`schedule` گیت‌هاب اکشنز best-effort است:
- برای ورک‌فلوهای تازه‌ساخته ممکن است ساعت‌ها تأخیر داشته باشد
- گیت‌هاب تضمینی برای دقت زمان‌بندی نمی‌دهد
- در عمل ثابت شد: ۱۲ اجرای اخیر همه `workflow_dispatch` بودند، صفر `schedule`

کرون ورسل قابل اتکاست و هر ۵ دقیقه دقیق فایر می‌شود. کارش فقط یک کار سبک است: صدا زدن API گیت‌هاب برای اجرای ورک‌فلو. این کار کمتر از یک ثانیه طول می‌کشد و کاملاً با مدل سرورلس سازگار است.

**اصل تفکیک:** ورسل «کی» را تعیین می‌کند، گیت‌هاب «چه» را اجرا می‌کند.

### ۳.۱. ترتیب موج‌ها

```
موج ۱: artdir → branding → content
موج ۲: analytics → intel → lead
موج ۳: design → seo → seocontent
موج ۴: design-ir → dev → farsiui
موج ۵: vibefarsi → qa
موج ۶: inspector
```

هر تیک فقط **یک تیم** اجرا می‌کند. چرخه کامل: ۱۵ تیک ≈ ۷۵ دقیقه.

### ۳.۲. مدیریت خطا در هر سطح

| سطح | خطا | رفتار |
|---|---|---|
| ساب‌ایجنت دانش | هر خطا | نادیده، تیم با دانش قبلی ادامه می‌دهد |
| فراخوانی LLM | 429/503/تایم‌اوت | تعویض خودکار مدل، ادامه همان کار |
| فراخوانی LLM | همه مدل‌ها خراب | تیم failed، دلیل ثبت می‌شود |
| تیم | exception | team_runs=failed، چرخه ادامه می‌دهد |
| تیم | running بیش از ۱۵ دقیقه | failed با دلیل تایم‌اوت |
| ورکر | کرش کامل | تیک بعدی از همان نقطه ادامه می‌دهد |
| چرخه | همه تیم‌ها تمام شدند | finishCycle، قفل آزاد می‌شود |

**قانون طلایی:** هیچ خطایی در یک تیم، تیم‌های دیگر یا چرخه را متوقف نمی‌کند. فقط چرخه‌ای که همه تیم‌هایش تمام شده‌اند بسته می‌شود.

## ۴. تغییرات لازم برای پیاده‌سازی

### ۴.۱. حذف کرون قدیمی ورسل

```diff
// vercel.json
{
  "buildCommand": "next build",
- "crons": [{"path": "/api/cron/cycle-tick", "schedule": "*/2 * * * *"}],
+ "crons": [{"path": "/api/cron/dispatch-worker", "schedule": "*/5 * * * *"}],
  "framework": "nextjs",
  "outputDirectory": ".next"
}
```

فایل `app/api/cron/cycle-tick/route.ts` حذف شود.

### ۴.۲. اندپوینت دیسپچر جدید

`app/api/cron/dispatch-worker/route.ts`:
- احراز با CRON_SECRET (الگوی موجود)
- خواندن چرخه فعال از Supabase
- اگر چرخه فعالی نیست و auto_start فعال است: صدا زدن workflow_dispatch با action=start-cycle
- اگر چرخه فعالی هست: صدا زدن workflow_dispatch بدون action (ادامه چرخه)
- فقط یک POST سبک به api.github.com؛ هیچ کد سنگینی اجرا نمی‌کند

```typescript
// شبه‌کد
const res = await fetch(
  'https://api.github.com/repos/masoudroot/thailandgard-dashboard/actions/workflows/cycle-worker.yml/dispatches',
  {
    method: 'POST',
    headers: {
      'Authorization': `Bearer ${GITHUB_TOKEN}`,
      'Accept': 'application/vnd.github+json',
    },
    body: JSON.stringify({ ref: 'master', inputs: { action } }),
  }
);
```

### ۴.۳. محافظ هم‌پوشانی در گیت‌هاب اکشنز

```yaml
# .github/workflows/cycle-worker.yml
concurrency:
  group: cycle-worker
  cancel-in-progress: false
```

این تضمین می‌کند هرگز دو اجرای ورکر هم‌زمان نباشند.

### ۴.۴. ادعای اتمیک تیم (جلوگیری از اجرای دوباره)

در `worker/cycle-worker.ts`، قبل از `runSingleTeam`:

```sql
-- فقط اگر هنوز کسی ادعایش نکرده
UPDATE team_runs
SET status = 'running', started_at = now()
WHERE cycle_id = $1 AND team = $2 AND status = 'pending'
RETURNING id;
```

اگر صفر ردیف برگشت، یعنی تیم دیگری قبلاً شروعش کرده؛ ورکر خارج می‌شود.

### ۴.۵. حذف schedule از ورک‌فلو (اختیاری ولی توصیه‌شده)

```diff
 on:
-  schedule:
-    - cron: '*/5 * * * *'
   workflow_dispatch:
```

با این کار، تنها محرک ورکر دیسپچر ورسل است. هیچ دو زمان‌بندی با هم رقابت نمی‌کنند.

## ۵. امنیت و رازها

| راز | کجا | دسترسی |
|---|---|---|
| GITHUB_TOKEN | Vercel env | فقط دیسپچر ورسل (POST به api.github.com) |
| SUPABASE_SERVICE_ROLE_KEY | GitHub Secrets + Vercel env | ورکر و API |
| CRON_SECRET | Vercel env | احراز کرون ورسل |
| MANAGER_API_TOKEN | Vercel env | احراز داشبورد |

GITHUB_TOKEN فقط به `actions:write` نیاز دارد (اسکوپ حداقلی).

## ۶. مانیتورینگ و هشدار

| متریک | منبع | آستانه هشدار |
|---|---|---|
| تیک بدون پیشرفت | team_runs.updated_at | بیش از ۱۵ دقیقه |
| چرخه باز بیش از ۴ ساعت | cycles.started_at | هشدار تلگرام |
| تیم failed | team_runs.status | ثبت در گزارش، نه هشدار فوری |
| دیسپچر ورسل خطا داد | لاگ ورسل | بررسی دستی |

واچ‌داگ موجود (هر ۳۰ دقیقه) این‌ها را چک می‌کند و فقط در صورت مشکل واقعی پیام می‌دهد.

## ۷. مسیر مهاجرت از وضعیت فعلی

1. **حذف کرون قدیمی:** ویرایش vercel.json + حذف route.ts + پوش
2. **ساخت دیسپچر:** فایل route.ts جدید + پوش
3. **محافظ هم‌پوشانی:** ویرایش workflow + پوش
4. **ادعای اتمیک:** ویرایش cycle-worker.ts + پوش
5. **تست:** workflow_dispatch دستی → یک تیم اجرا شود → تیک بعدی تیم بعدی
6. **نظارت:** یک چرخه کامل (حدود ۷۵ دقیقه) زیر نظر

**نکته:** چرخه گیرکرده فعلی (`run-20261015142430`) با همین معماری جدید ادامه پیدا می‌کند؛ نیازی به حذف و شروع دوباره نیست. ورکر از روی team_runs موجود، تیم بعدی را پیدا می‌کند.
