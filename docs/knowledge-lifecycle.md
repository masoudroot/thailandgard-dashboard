# چرخه حیات و تازگی دانش تیم‌ها

> سند طراحی — تیم ۶ از ۱۰ تیم مدیریت دانش تایلندگرد
> وضعیت: پیش‌نویس طراحی برای پیاده‌سازی
> وابستگی‌ها: جدول‌های `team_knowledge` ،`knowledge_chunks` ،`knowledge_history` (مهاجرت `20261015140000_team_knowledge.sql`) و `lib/rag.ts`

## ۱. مسئله

دانش تیم‌ها امروز فقط دو وضعیت دارد: هست یا نیست. دانشی که شش ماه پیش درباره یک API ثبت شده، امروز ممکن است غلط باشد ولی همچنان در پرامپت تیم تزریق می‌شود. از آن بدتر، هیچ‌کس مسئول «کهنه شدن» دانش نیست. این سند یک چرخه حیات کامل تعریف می‌کند: تولد با تاریخ انقضا، بازبینی دوره‌ای، آرشیو بدون حذف، و تزریق فقط دانش تازه در RAG.

### اصول

1. **حذف فیزیکی ممنوع.** دانش آرشیو می‌شود، پاک نمی‌شود. حافظه سازمانی برگشت‌پذیر است.
2. **انقضا در لحظه تولد.** هر دانش موقع ثبت یک نوع دارد و نوعش تاریخ انقضایش را تعیین می‌کند؛ نه بعداً، نه دستی.
3. **تازه‌بودن پیش‌فرض RAG است.** مسیری که دانش را به پرامپت می‌رساند فقط وضعیت‌های سالم را می‌بیند؛ بقیه باید عمداً خواسته شوند.
4. **بازبینی کارِ ساب‌ایجنت دانش است، نه مسعود.** انسان فقط استثناها را می‌بیند.

## ۲. مدل داده: فیلدهای زمانی و وضعیتی

روی `team_knowledge` شش ستون تازه می‌نشیند (مهاجرت جدید، فقط DDL):

| ستون | نوع | پیش‌فرض | معنی |
|---|---|---|---|
| `knowledge_type` | text | `'source_note'` | نوع دانش؛ سیاست انقضا را تعیین می‌کند (بخش ۳) |
| `status` | text | `'active'` | یکی از `active` ،`needs_review` ،`archived` |
| `reviewed_at` | timestamptz | NULL | آخرین باری که صحت دانش تأیید شد |
| `expires_at` | timestamptz | NULL | تاریخی که دانش منقضی می‌شود؛ NULL یعنی بدون انقضای خودکار |
| `archived_at` | timestamptz | NULL | زمان آرشیو |
| `review_count` | integer | ۰ | چند بار بازبینی شده |

ایندکس‌ها:

```sql
create index if not exists team_knowledge_status_idx on team_knowledge(team, status);
create index if not exists team_knowledge_expires_idx on team_knowledge(expires_at)
  where status = 'active';
```

نکته مهم: `updated_at` یعنی «متن عوض شد» و `reviewed_at` یعنی «صحتش تأیید شد». این دو را قاطی نکنید؛ ویرایش متن، بازبینی نیست.

### ۲.۱. انواع دانش (`knowledge_type`)

| نوع | تعریف | مثال |
|---|---|---|
| `technical` | وابسته به نسخه، API، ابزار، قیمت، رفتار پلتفرم | «پارامتر X در API گوگل از نسخه ۳ حذف شد» |
| `critic_lesson` | درس استخراج‌شده از حکم منتقد درباره خروجی خودمان | «پرهیز از کلیشه سرزمین لبخندها در شعار» |
| `source_note` | نکته آموخته‌شده از منبع آموزشی بیرونی | «خلاصه فصل ۴ کتاب…» |
| `principle` | اصل ماندگار طراحی، نگارش، رفتار حرفه‌ای | «در چیدمان راست‌چین، لیبل راست و عدد چپ» |

نوع در لحظه ثبت توسط نویسنده (ساب‌ایجنت دانش یا API) انتخاب می‌شود و بعداً قابل اصلاح است؛ هر اصلاح نوع در `knowledge_history` با action جدید `retype` ثبت می‌شود.

## ۳. سیاست تازگی به تفکیک نوع

انقضا از `created_at` یا از آخرین `reviewed_at` (هر کدام تازه‌تر) حساب می‌شود:

| نوع | عمر (TTL) | هشدار پیش از انقضا | منطق |
|---|---|---|---|
| `technical` | ۳۰ روز | ۷ روز مانده | API و ابزار سریع عوض می‌شوند؛ دانش فنی کهنه = دانش غلط |
| `source_note` | ۹۰ روز | ۱۴ روز مانده | منبع ممکن است به‌روز شده باشد؛ ارزش بازخوانی دارد |
| `critic_lesson` | ۱۸۰ روز | ۳۰ روز مانده | درس رفتاری دیر کهنه می‌شود ولی عادت تیم عوض می‌شود؛ باید بازبینی شود |
| `principle` | بدون انقضای خودکار | بازبینی سالانه | اصل ماندگار است؛ فقط سالی یک بار چشم‌انداز می‌خواهد |

قانون محاسبه:

```
effective_start = max(created_at, reviewed_at ?? created_at)
expires_at = effective_start + TTL(type)   -- برای principle: NULL
```

یعنی هر بازبینی موفق، ساعت انقضا را صفر می‌کند. دانشی که مرتب تأیید می‌شود، عملاً همیشه تازه می‌ماند؛ دانشی که هیچ‌کس سراغش نمی‌رود، خودش می‌میرد. این دقیقاً همان رفتاری است که می‌خواهیم.

### استثنا: دانش بحرانی بدون انقضا

اگر `knowledge_type = 'technical'` ولی محتوا چیزی مثل «کلید دسترسی» یا «آدرس ثابت سرویس» است، نویسنده می‌تواند `expires_at` را دستی NULL کند با ذکر دلیل در محتوا. این استثناست، نه قاعده.

## ۴. چه کسی پرچم «نیاز به بازبینی» می‌زند؟

سه بازیگر، سه مسئولیت جدا:

### ۴.۱. کرون روزانه (ساعت ۰۴:۰۰ تهران) — داور بی‌طرف

یک کرون سبک، فقط SQL، بدون LLM:

```sql
update team_knowledge
set status = 'needs_review', updated_at = now()
where status = 'active'
  and expires_at is not null
  and expires_at < now();
```

- idempotent است؛ اجرای دوباره بی‌اثر است.
- هیچ تصمیم محتوایی نمی‌گیرد؛ فقط «وقتش رسیده» را اعلام می‌کند.
- نتیجه (تعداد پرچم‌خورده به تفکیک تیم) در لاگ مدیریتی ثبت می‌شود تا در داشبورد دیده شود.

### ۴.۲. ساب‌ایجنت دانش هر تیم — بازبین واقعی

ساب‌ایجنت دانش (طراحی تیم ۴) در شروع نوبت هر تیم، پیش از هر کار دیگری، صف بازبینی تیم خودش را خالی می‌کند:

1. همه ردیف‌های `status = 'needs_review'` تیم خودش را می‌خواند.
2. برای هر کدام: منبع اصلی را باز می‌کند (اگر `source` URL است) یا در دانش تازه جست‌وجو می‌کند.
3. سه حکم ممکن:
   - **تأیید:** هنوز درست است ← `status='active'` ،`reviewed_at=now()` ،`expires_at` تازه از نو حساب می‌شود، `review_count + 1`. چانک‌های RAG دست نمی‌خورند (متن عوض نشده).
   - **اصلاح:** هسته درست ولی جزئیات عوض شده ← متن به‌روز می‌شود (مسیر update معمول + `recordHistory`)، بعد مثل تأیید.
   - **آرشیو:** دیگر درست نیست یا بی‌ربط شده ← `status='archived'` ،`archived_at=now()`.
4. اگر نتوانست تصمیم بگیرد (منبع در دسترس نیست)، دانش را در `needs_review` نگه می‌دارد و دلیل را در گزارش نوبتش می‌نویسد؛ کرون بعدی دوباره نمی‌زند چون وضعش عوض نشده.

قرارداد مهم: **گرسنگی دانش ممنوع.** اگر بیش از ۵۰٪ دانش فعال یک تیم در `needs_review` باشد، ساب‌ایجنت موظف است در همان نوبت همه را تعیین‌تکلیف کند، نه اینکه بگذارد برای بعد.

### ۴.۳. پرچم پیش‌دستانه (اختیاری ولی توصیه‌شده)

ساب‌ایجنت دانش موقع خواندن منابع تازه، اگر بفهمد دانش فعالی (حتی با انقضای نرسیده) غلط شده، می‌تواند مستقیم `needs_review` بزند با ذکر دلیل در گزارش. انقضای خودکار کف است، نه سقف.

## ۵. آرشیو: مرگ بدون حذف

- آرشیو یعنی `status='archived'` + `archived_at=now()`. ردیف `team_knowledge` و تاریخچه‌اش سر جایش می‌ماند.
- چانک‌های `knowledge_chunks` **حذف نمی‌شوند**. دلیل: بازیابی باید فوری باشد، نه اینکه دوباره امبدینگ بسازیم و پول بدهیم.
- فیلتر RAG (بخش ۶) آرشیوشده‌ها را نمی‌بیند، پس از نظر تیم «مرده»‌اند ولی از نظر سیستم «قابل احیا»‌اند.
- بازیابی: `status='active'` + `reviewed_at=now()` + `expires_at` تازه + `archived_at=NULL`. در داشبورد دکمه «بازیابی» در زبانه آرشیو هر تیم.
- حذف فیزیکی فقط با تأیید صریح مسعود از داشبورد و فقط برای داده اشتباهِ ثبت‌شده (مثلاً تست) مجاز است؛ آن هم با ثبت در `knowledge_history` با action جدید `purge`.

## ۶. فیلتر تازگی در مسیر RAG

### ۶.۱. تصمیم معماری: بدون تغییر امضای RPC

تابع `match_knowledge_chunks(query_embedding, match_count, filter_team)` دست نمی‌خورد. دلیل: این تابع در چند جا صدا زده می‌شود (`lib/rag.ts` و `app/api/knowledge/search/route.ts`) و تغییر امضایش ریسک ناسازگاری دارد. فیلتر تازگی در لایه TypeScript، بعد از RPC و قبل از قالب‌بندی اعمال می‌شود؛ جایی که امروز `retrieveKnowledge` چانک‌های خالی را حذف می‌کند.

### ۶.۲. الگوریتم `retrieveKnowledge` جدید

```
۱. RPC را مثل قبل صدا بزن (با match_count بزرگ‌تر از limit، مثلاً ۳ برابر،
   چون بخشی از نتایج با فیلتر تازگی حذف می‌شوند).
۲. knowledge_id های یکتای نتایج را بگیر.
۳. یک کوئری batch به team_knowledge بزن:
     select id, status, reviewed_at, expires_at from team_knowledge where id in (...)
   (fail-soft: اگر این کوئری خطا داد، همه نتایج را نگه دار؛
   نداشتن فیلتر بهتر از نداشتن دانش است.)
۴. نگه دار فقط ردیف‌هایی که status = 'active' است.
۵. اگر تعداد active ها از limit کمتر شد و ردیف needs_review هست،
   آن‌ها را با برچسب «[نیازمند بازبینی — با احتیاط استفاده کن]» اضافه کن
   تا سقف limit. (گرسنگی دانش، بخش ۴.۲)
۶. مثل قبل قالب‌بندی و برگردان.
```

نکته: `KnowledgeChunkRow` باید `knowledge_id` را هم برگرداند. امروز این ستون در `knowledge_chunks` هست (مهاجرت آن را اضافه کرده) ولی در تایپ ردیف `lib/rag.ts` نیست؛ اضافه شود.

### ۶.۳. چرا `needs_review` با برچسب و نه حذف کامل؟

دو نیروی مخالف: (الف) دانش مشکوک نباید بی‌سروصدا در تصمیم تزریق شود؛ (ب) تیم نباید به‌خاطر صف بازبینیِ شلوغ، بی‌دانش بماند. راه‌حل: مشکوکِ برچسب‌دار بهتر از مشکوکِ پنهان و بهتر از خلأ است. برچسب به مدل می‌گوید «خودت بسنج»، و چون ساب‌ایجنت دانش موظف به خالی کردن صف است (بخش ۴.۲)، این حالت موقتی است.

### ۶.۴. جست‌وجوی دستی (`/api/knowledge/search`)

در UI جست‌وجو، فیلتر وضعیت یک انتخاب کاربر است: پیش‌فرض `active`، با گزینه‌های `needs_review` و `archived` و `all`. این تنها جایی است که دانش آرشیوشده عمداً دیده می‌شود.

## ۷. APIهای تازه (قرارداد برای تیم ۱۱)

| متد و مسیر | کار |
|---|---|
| `GET /api/manager/knowledge/review-queue?team=` | صف `needs_review` یک تیم (یا همه) با سن انقضا |
| `POST /api/manager/knowledge/:id/review` | بدنه: `{ verdict: 'confirm' \| 'revise' \| 'archive', content? }` — همان کاری که ساب‌ایجنت می‌کند، برای بازبینی دستی |
| `POST /api/manager/knowledge/:id/restore` | بازیابی از آرشیو |
| `GET /api/manager/knowledge/archived?team=` | زبانه آرشیو داشبورد |

همه این‌ها از همان `recordHistory` و `indexKnowledge`/`deleteKnowledgeIndex` موجود استفاده می‌کنند؛ منطق تازه فقط مدیریت `status` و `expires_at` است.

### ۷.۱. تغییر در `indexKnowledge`

امضای تازه (پارامتر اختیاری آخر، سازگار با عقب):

```ts
indexKnowledge(knowledgeId, team, title, content, opts?: {
  knowledgeType?: 'technical' | 'critic_lesson' | 'source_note' | 'principle';
  source?: string;   // امروز source همیشه 'team-lesson' هاردکد است؛ باید واقعی شود
})
```

- `knowledge_type` در `team_knowledge` ذخیره می‌شود (این کار را API ثبت دانش انجام می‌دهد، نه خود `indexKnowledge`).
- `expires_at` از قانون بخش ۳ حساب و در همان تراکنش ثبت دانش ست می‌شود.
- باگ موجود که باید همین‌جا درست شود: `source` در چانک‌ها امروز همیشه `'team-lesson'` است؛ باید منبع واقعی دانش باشد تا بخش ۴.۲ بتواند «منبع اصلی را باز کند».

## ۸. کرون‌ها و زمان‌بندی

| کرون | زمان | کار |
|---|---|---|
| `knowledge-expiry-tick` | روزانه ۰۴:۰۰ تهران | SQL بخش ۴.۱ + ثبت تعداد در لاگ مدیریتی |
| بازبینی ساب‌ایجنت دانش | شروع نوبت هر تیم در هر چرخه | خالی کردن صف `needs_review` تیم خودش (بخش ۴.۲) |
| گزارش تازگی هفتگی | شنبه ۰۸:۰۰، در گزارش مدیریتی | درصد دانش فعال/نیازمند بازبینی/آرشیو به تفکیک تیم |

## ۹. معیارها (خوراک امتیاز «دانشمند حوزه»)

`lib/knowledge-score.ts` امروز تازگی را فقط با سن `created_at` می‌سنجد (۷ روز کامل، ۹۰ روز صفر). با این طرح، مؤلفه تازگی باید بازنویسی شود:

- مخرج: فقط دانش‌های `active`
- تازگی هر دانش = فاصله تا `expires_at` (نه سن از تولد)؛ `principle`‌ها همیشه کامل
- جریمه: هر دانش `needs_review` که بیش از ۷ روز در صف مانده، ۲ نمره از امتیاز تیم کم می‌کند (تا سقف ۲۰)

این یعنی امتیاز، «مدیریت فعالانه» را جایزه می‌دهد نه فقط «جوان بودن» را.

## ۱۰. ریسک‌ها و تصمیم‌های باز

1. **هزینه بازبینی LLM.** ساب‌ایجنت دانش برای هر ردیف `needs_review` باید منبع را بخواند و حکم بدهد. اگر تیمی ۴۰ ردیف انباشته داشته باشد، یک نوبت کامل می‌بلعد. پیشنهاد: سقف ۱۰ بازبینی در هر نوبت؛ بقیه در نوبت‌های بعد. (تصمیم با تیم ۴)
2. **انقضای `critic_lesson` در ۱۸۰ روز.** اگر درسی واقعاً ماندگار بود، بازبینی‌اش تشریفاتی می‌شود. جایگزین: `critic_lesson` هم مثل `principle` بدون انقضا ولی با بازبینی سالانه؟ فعلاً ۱۸۰ روز می‌ماند تا داده واقعی ببینیم؛ بعد از ۳ ماه بازنگری شود.
3. **چانک‌های یتیم.** اگر ردیف `team_knowledge` دستی از دیتابیس پاک شود، `on delete cascade` چانک‌ها را می‌برد؛ درست است. ولی `knowledge_history` هم cascade می‌شود و ردپا می‌ماند؟ نه — هیستوری هم پاک می‌شود. برای `purge` دستی این قابل‌قبول است چون فقط با تأیید مسعود رخ می‌دهد.
4. **ساعت سرور.** همه مقایسه‌های زمانی با `now()` دیتابیس انجام می‌شود، نه ساعت ورکر؛ اختلاف ساعت ورکرها بی‌اثر است.

## ۱۱. ترتیب پیاده‌سازی پیشنهادی

1. مهاجرت DDL (بخش ۲) + ایندکس‌ها
2. `indexKnowledge` با `knowledge_type` و `expires_at` + رفع باگ `source` هاردکد (بخش ۷.۱)
3. فیلتر تازگی در `retrieveKnowledge` (بخش ۶) — اثر فوری روی کیفیت پرامپت
4. کرون `knowledge-expiry-tick`
5. APIهای بخش ۷
6. بازنویسی مؤلفه تازگی در `knowledge-score.ts`
7. UI صف بازبینی و زبانه آرشیو (تیم ۱۰)
8. اتصال به ساب‌ایجنت دانش (تیم ۴): خواندن صف در شروع نوبت + حکم سه‌گانه
