# اشتراک دانش بین تیم‌ها (تیم ۷)

سند طراحی: چطور دانش یک تیم به تیم‌های دیگر برسد، بدون اینکه پرامپت‌ها را آلوده کند.

## وضعیت فعلی

- `team_knowledge`: هر رکورد یک مالک دارد (`team`).
- `knowledge_chunks`: چانک‌ها با ستون `team` ایندکس می‌شوند.
- RPC ‏`match_knowledge_chunks`‏ فقط با `filter_team` جست‌وجو می‌کند.
- `buildKnowledgePromptSection` فقط دانش همان تیم را به پرامپت تزریق می‌کند.

نتیجه: دانش در سیلوی تیم خودش گیر می‌کند. اگر برندینگ یاد بگیرد «سرزمین لبخندها» کلیشه است، تیم محتوا همچنان همان کلیشه را در متن‌ها تکرار می‌کند.

## تصمیم‌های طراحی

### ۱. تگ‌گذاری تیم‌های مرتبط: ترکیبی (خودکار + تأیید انسانی)

نه دستیِ صرف (فراموش می‌شود)، نه خودکارِ صرف (آلودگی می‌آورد).

**خودکار:** هنگام استخراج دانش، یک فراخوانی LLM با ورودی «عنوان + محتوا + دامنه» و «مأموریت هر ۱۵ تیم از TEAM_META» برای هر تیم نمره ارتباط ۰ تا ۱ و یک جمله دلیل تولید می‌کند.

**آستانه:**
- نمره ≥ ۰٫۸۵: اشتراک خودکار انجام می‌شود.
- ۰٫۶ تا ۰٫۸۵: پیشنهاد در داشبورد می‌ماند تا مالک دانش تأیید یا رد کند.
- زیر ۰٫۶: اشتراک نمی‌شود.

**دستی:** مالک دانش در داشبورد همیشه می‌تواند تیم اضافه یا کم کند؛ تصمیم انسانی بر نمره LLM می‌چربد.

### ۲. باخبر شدن تیم B: رویدادِ لاگ + RAG غیرفعال

پوشِ واقعی (پیام/صف) لازم نیست؛ تیم‌ها زمان‌بندی‌شده اجرا می‌شوند و پیامِ فوری جایی برای نشستن ندارد. به‌جایش دو لایه:

**لایه غیرفعال (اصلی):** چانک‌های مشترک در `visible_to` تیم B هم ثبت می‌شوند؛ پس در RAG بعدی تیم B خودبه‌خود بالا می‌آیند. هیچ کد اضافه‌ای در مسیر اجرای تیم لازم نیست.

**لایه رویداد (حسابرسی و آگاهی):** جدول `knowledge_share_events` هر اشتراک را با «از کدام تیم، به کدام تیم، چرا» ثبت می‌کند. ساب‌ایجنت دانش هر تیم (قدم ۱ پلن) در شروع نوبتش رویدادهای تازه مربوط به خودش را می‌خواند و می‌تواند صریحاً آن‌ها را در تصمیم‌هایش لحاظ کند. داشبورد هم نشان «دانش مشترک تازه» برای هر تیم دارد.

### ۳. یک رکورد با چند تگ، نه کپی جدا

یک رکورد در `team_knowledge` می‌ماند؛ مالک در ستون `team` حفظ می‌شود (مرجع ویرایش و اصالت) و تیم‌های مشترک در آرایه `shared_with`.

چرا نه کپی:
- ویرایش مالک خودکار به همه می‌رسد (چانک‌ها دوباره ایندکس می‌شوند).
- حذف، آبشاری و تمیز است (کلید خارجی موجود).
- تناقض نسخه‌ها پیش نمی‌آید (دو کپی که یکی به‌روز شده و دیگری نه).

### ۴. جلوگیری از آلودگی: سه لایه دفاع

**الف) دروازه ارتباط در زمان اشتراک:** فقط نمره ≥ ۰٫۶ (بخش ۱). دانش خیلی تخصصی اصلاً به تیم نامرتبط نمی‌رسد.

**ب) جریمه رتبه در زمان بازیابی:** چانک مشترک در امتیاز نهایی ضریب ۰٫۸ می‌گیرد تا در تساوی، دانش خودِ تیم ببرد. در RPC یا پس‌پردازش اعمال می‌شود.

**ج) سهمیه در تزریق پرامپت:** از ۵ چانک تزریقی، حداکثر ۲ چانک می‌تواند مشترک باشد (پیش‌فرض: ۴ خودی + ۱ مشترک؛ قابل تنظیم در settings). پرامپت تیم Y هرگز زیر خروار دانش تیم X دفن نمی‌شود.

**د) برچسب منشأ:** چانک مشترک با «[مشترک از تیم برندینگ]» برچسب می‌خورد تا مدل وزن آن را درست بسنجد و در صورت تعارض، منشأ مشخص باشد.

**تعارض دانش:** اگر دو دانش مشترک با هم ناسازگار شدند (مثلاً لحن رسمی در برابر محاوره‌ای)، هر دو نگه داشته می‌شوند ولی فیلد `scope` (دامنه کاربرد) تعیین‌کننده است؛ بازیابی به تطابق دامنه اولویت می‌دهد و تناقض در داشبورد برای داوری انسانی پرچم می‌خورد. حل خودکار تناقض ممنوع.

### ۵. مثال عینی: «سرزمین لبخندها»

دانش استخراج‌شده توسط برندینگ (از رد منتقد):

- عنوان: «پرهیز از کلیشه سرزمین لبخندها در شعار»
- محتوا: «کلیشه رایج صنعت گردشگری است؛ تمایز صفر. قاعده آینده: شعار باید متمایز و متکی به پشتوانه واقعی باشد.»
- دامنه (scope): «شعار، تیتر اصلی و پیام‌های کلیدی برند»
- شاهد: رد منتقد چرخه اخیر

تگ‌گذاری LLM:

| تیم | نمره | دلیل |
|---|---|---|
| content | ۰٫۹ | متن‌های سایت همان پیام برند را تکرار می‌کنند |
| seo | ۰٫۷۸ | تایتل و متا دیسکریپشن‌ها شعار را بازنشر می‌کنند |
| seocontent | ۰٫۷۲ | مقالات سئویی لحن برند را حمل می‌کنند |
| design | ۰٫۴۵ | زیر آستانه؛ رد شد |

اشتراک خودکار با content (۰٫۹ ≥ ۰٫۸۵)؛ پیشنهاد برای seo و seocontent در داشبورد تا مالک تأیید کند.

در چرخه بعد، وقتی تیم content برای «بازنویسی لندینگ تور پوکت» RAG می‌زند، چانک مشترک با برچسب «[مشترک از تیم برندینگ]» بالا می‌آید و مجری از «سرزمین لبخندها» در بدنه متن هم پرهیز می‌کند، نه فقط در شعار.

اگر تیم seo بعداً بفهمد این قاعده در متا دیسکریپشن ۱۶۰ کاراکتری جواب نمی‌دهد، روی همان دانش «بازخورد منفی» ثبت می‌کند؛ مالک (برندینگ) می‌بیند و دامنه را تنگ‌تر می‌کند یا اشتراک با seo را لغو می‌کند.

## تغییرات اسکیما (افزودنی، بدون شکستن قرارداد فعلی)

```sql
-- team_knowledge: ستون team می‌ماند = مالک
alter table team_knowledge add column if not exists shared_with text[] not null default '{}';
alter table team_knowledge add column if not exists share_score jsonb not null default '{}'; -- {"content": 0.9}
alter table team_knowledge add column if not exists scope text; -- دامنه کاربرد
alter table team_knowledge add column if not exists auto_shared boolean not null default false;

-- knowledge_chunks: دیده‌شدن برای چند تیم
alter table knowledge_chunks add column if not exists visible_to text[] not null default '{}';
create index if not exists knowledge_chunks_visible_to_idx on knowledge_chunks using gin (visible_to);

-- فید رویدادهای اشتراک
create table if not exists knowledge_share_events (
  id uuid primary key default gen_random_uuid(),
  knowledge_id uuid not null references team_knowledge(id) on delete cascade,
  from_team text not null,
  to_team text not null,
  reason text,
  created_at timestamptz not null default now()
);
create index if not exists knowledge_share_events_to_team_idx on knowledge_share_events(to_team, created_at desc);
```

تغییر RPC ‏`match_knowledge_chunks`‏ (بدون تغییر امضا؛ فقط شرط WHERE):

```sql
-- قبل: team = filter_team
-- بعد:
where (filter_team is null
   or knowledge_chunks.team = filter_team
   or filter_team = any(knowledge_chunks.visible_to))
```

## جریان اشتراک (قدم‌به‌قدم)

۱. استخراج دانش توسط تیم A (مثل الان) ← رکورد با `team = A`.
۲. تگ‌گذاری LLM: نمره و دلیل برای هر ۱۵ تیم.
۳. اگر نمره ≥ ۰٫۸۵: `shared_with` به‌روز می‌شود، `auto_shared = true`.
۴. اگر ۰٫۶ تا ۰٫۸۵: پیشنهاد در داشبورد؛ با تأیید مالک، مرحله ۳.
۵. ایندکس مجدد چانک‌ها با `visible_to = shared_with` (از `indexKnowledge` موجود در lib/rag.ts استفاده می‌شود).
۶. درج ردیف در `knowledge_share_events` برای هر تیم مقصد + ثبت در `knowledge_history`.
۷. لغو اشتراک: حذف از `shared_with`، ایندکس مجدد، رویداد «لغو» در همان جدول (با فیلد reason).

## توابع پیشنهادی (lib/knowledge-sharing.ts)

- `suggestShareTargets(knowledgeId): Promise<Array<{team, score, reason}>>` — تگ‌گذاری LLM.
- `shareKnowledge(knowledgeId, teams[], opts {reason?, auto?})` — به‌روزرسانی shared_with + ایندکس مجدد + رویداد.
- `unshareKnowledge(knowledgeId, team)` — لغو.
- `getNewSharesForTeam(team, since)` — رویدادهای تازه برای ساب‌ایجنت دانش.
- `retrieveKnowledge` موجود: پارامتر `sharedLimit` می‌گیرد (پیش‌فرض ۱ از ۵).

## API مدیر (الگو: POST /api/manager/knowledge موجود)

- `POST /api/manager/knowledge/[id]/share` با بدنه `{teams: string[], reason?: string}`
- `DELETE /api/manager/knowledge/[id]/share/[team]`
- `GET /api/manager/knowledge/shares?team=X&since=...` — فید رویدادها

## نکته‌های مرزی

- دانش مشترک «فقط خواندنی» برای تیم مقصد است؛ ویرایش فقط با مالک. بازخورد از طریق رویداد/پرچم، نه ویرایش مستقیم.
- اگر مالک دانش حذف شود، رکورد و چانک‌ها آبشاری حذف می‌شوند (رفتار فعلی).
- سقف: هر دانش حداکثر با ۵ تیم مشترک شود؛ بیشتر از آن یعنی دانش خیلی عام است و باید به «دانش پایه مشترک» ارتقا پیدا کند (تصمیم آینده).
- امتیازدهی مجدد دوره‌ای: اگر نمره ارتباط دانشی با رفتار واقعی (کلیک/استفاده در RAG) نخواند، در بازبینی دوره‌ای پرچم می‌خورد.
