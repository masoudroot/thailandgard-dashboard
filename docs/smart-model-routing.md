# معماری مدل‌سوییچینگ هوشمند

سند طراحی: چطور سیستم مدل‌های هوش مصنوعی هیچ‌وقت خطا ندهد.
تاریخ: ۱۴۰۵/۰۷/۲۳

## ۱. وضع فعلی و شکاف‌ها

سیستم فعلی (`lib/llm.ts`) این‌طور کار می‌کند:

- هر تیم یک مدل اصلی دارد (`team_models` در settings).
- اگر خطای قابل‌تلاش رخ دهد (429، 503، تایم‌اوت)، تابع `findWorkingModel` یک بار دنبال جایگزین می‌گردد.
- `findWorkingModel` فقط ۳ مدل ثابتِ هاردکدشده (`KNOWN_FALLBACK_MODELS`) را روی هر درگاه تست می‌کند.
- امبدینگ (`getEmbedding` در `lib/rag.ts`) هیچ جایگزینی ندارد؛ اگر درگاه امبدینگ بخوابد، کل RAG می‌میرد.

شکاف‌ها نسبت به خواسته مسعود:

| خواسته | وضع فعلی |
|---|---|
| هر مدل ریت‌لیمیت جدا دارد؛ اول مدل دیگر همان API | فقط ۳ مدل هاردکدشده تست می‌شود، نه همه مدل‌های API |
| جایگزین باید «مدل خوب برای همان کار» باشد | هر مدلی که جواب بدهد قبول است، حتی مدل ضعیف |
| اگر سهمیه یک API تمام شد، برود API بعدی | ترتیب APIها ثابت و دستی است (غیرگمینای اول) |
| چند کلید گمینای = چند سهمیه جدا | کلیدها جدا دیده نمی‌شوند |
| امبدینگ هم همین منطق | هیچ جایگزینی ندارد |
| هیچ‌وقت خطا نبینیم | بعد از یک تلاش ناموفق، خطا به تیم برمی‌گردد |

## ۲. اصول طراحی

1. **رده‌بندی مدل‌ها.** هر مدل یک رده (tier) دارد: S قوی، A متعادل، B سبک. جایگزین هرگز از رده پایین‌تر از حداقل لازم تیم انتخاب نمی‌شود.
2. **زنجیره ۴ سطحی.** ترتیب جایگزینی ثابت است: مدل دیگر همان API ← کلید دیگر همان ارائه‌دهنده ← API دیگر ← رده بالاتر. هرگز مستقیم سراغ API دیگر نمی‌رویم وقتی همان API مدل سالم دارد.
3. **حافظه سلامت.** وضعیت هر جفت (درگاه، مدل) ذخیره می‌شود: سالم، ریت‌لیمیت (موقت)، سهمیه‌تمام (نیمه‌موقت)، کلیدخراب (دائم تا اصلاح)، مدل‌منسوخ (دائم). تصمیم روی حافظه است نه حدس.
4. **بدون تنزل دائمی.** جایگزینیِ هر فراخوانی موقت است. مدل اصلی تیم فقط وقتی عوض می‌شود که یا منسوخ شده باشد یا ۵ بار پیاپی جایگزینِ هم‌رده یا بهتر جواب داده باشد.
5. **امبدینگ شهروند درجه‌یک است.** همان زنجیره و همان حافظه سلامت برای امبدینگ هم پیاده می‌شود.

## ۳. رده‌بندی مدل‌ها (Tier)

### ۳.۱ تعریف رده‌ها

| رده | معنا | کاربرد |
|---|---|---|
| S | استدلال قوی، کدنویسی دقیق، داوری سخت‌گیرانه | dev، design، qa |
| A | تولید متن روان، تحلیل، ترجمه | content، seo، analytics |
| B | کارهای سبک و سریع: استخراج، دسته‌بندی، خلاصه کوتاه | ساب‌ایجنت‌های دانش |

### ۳.۲ نگاشت پیش‌فرض مدل به رده

این نگاشت در تنظیمات (`llm_model_tiers`) قابل ویرایش توسط مدیر است. الگوی پیش‌فرض:

**رده S:**
- `deepseek-v4`، `deepseek-v4-thinking`
- `glm-5.3`، `glm-5.2` (بدون پسوند flash)
- `qwen3.8`، `qwen3.5-omni` (بدون پسوند flash)
- `kimi-k3`
- `grok-4.7`
- `gemini-3.8-flash`، `gemini-3.5-pro`، `gemini-2.5-pro`

**رده A:**
- `glm-5.3-flash`، `glm-5.2-flash`
- `qwen3.8-flash`، `qwen3.5-flash`
- `deepseek-v4-flash`
- `gemini-2.5-flash`، `gemini-3.5-flash`، `gemini-3.6-flash`
- `kimi-k2`

**رده B:**
- `gemini-2.5-flash-lite`، `gemini-3.5-flash-lite`
- هر مدلی با `lite` یا `mini` یا `haiku` در نام

### ۳.۳ قانون خودکار رده‌بندی

مدل‌هایی که مدیر دستی رده‌بندی نکرده، با این قانون حدس زده می‌شوند (اولین تطبیق برنده است):

1. شامل `lite` یا `mini` یا `haiku` ← B
2. شامل `pro` یا `thinking` یا `deepseek-v4` (بدون flash) یا `opus` ← S
3. شامل `flash` ← A
4. `glm-5` بدون flash ← S
5. `qwen3` بدون flash ← S
6. `kimi-k3` ← S، `kimi-k2` ← A
7. پیش‌فرض ← A

هر بار که فهرست `/models` یک درگاه تازه‌سازی می‌شود، مدل‌های تازه با همین قانون رده‌بندی و در حافظه ثبت می‌شوند. مدیر می‌تواند هر کدام را دستی اصلاح کند.

## ۴. پروفایل کاری تیم‌ها

هر تیم یک «حداقل رده» دارد (`llm_team_min_tier` در settings، قابل ویرایش):

| تیم | حداقل رده | دلیل |
|---|---|---|
| dev | S | کدنویسی واقعی؛ مدل ضعیف کد خراب می‌دهد |
| design، design-ir | S | تولید کامپوننت دقیق |
| qa | S | داوری کد نیاز به دقت بالا دارد |
| inspector | A | بازبینی و پیشنهاد |
| content، seocontent | A | تولید محتوای فارسی روان |
| seo | A | تحلیل و تولید متا |
| branding، artdir | A | متن خلاقانه |
| analytics، intel، lead | A | تحلیل داده و بازار |
| vibefarsi، farsiui | A | رابط فارسی |
| ساب‌ایجنت دانش | B | استخراج و ثبت ساده |

قانون سفت: جایگزین هر تیم هرگز از حداقل رده آن تیم پایین‌تر نمی‌آید. اگر هیچ مدلی در رده لازم سالم نبود، به‌جای تنزل، خطای شفاف «هیچ مدل سالمی در رده لازم نیست» ثبت می‌شود تا مدیر باخبر شود.

## ۵. زنجیره جایگزینی (۴ سطح)

وقتی فراخوانی با مدل اصلی شکست خورد (خطای قابل‌تلاش)، روتر به این ترتیب کاندیدا می‌سازد:

**سطح ۱: مدل دیگر، همان API و همان کلید.**
همان درگاه تیم، مدل‌های دیگر با رده مساوی یا بالاتر که سالم‌اند. اول رده بالاتر، بعد بر اساس نرخ موفقیت اخیر. (ریت‌لیمیت معمولاً per-model است؛ پس همین‌جا بیشتر مشکلات حل می‌شود.)

**سطح ۲: کلید دیگر، همان ارائه‌دهنده.**
اگر همه مدل‌های آن کلید در cooldown هستند (سهمیه کلید تمام شده)، سراغ کلیدهای دیگر همان ارائه‌دهنده می‌رویم. مثلاً ۴ کلید گمینای ۴ سهمیه جدا دارند. ترتیب: مدلی هم‌نام مدل اصلی اگر روی آن کلید سالم است، وگرنه مدل‌های هم‌رده یا بالاتر.

**سطح ۳: ارائه‌دهنده دیگر.**
درگاه‌های ارائه‌دهنده متفاوت (مثلاً از گمینای به reformboss یا برعکس) به ترتیب اولویت مدیر (`llm_endpoint_priority`). در هر درگاه: مدل‌های هم‌رده یا بالاترِ سالم.

**سطح ۴: ارتقای اضطراری.**
اگر در هیچ درگاهی مدل هم‌رده سالم نبود، مدل‌های رده بالاتر (S برای تیمی که A می‌خواست) امتحان می‌شوند. این آخرین راه است؛ بهتر از خطا دادن.

**هرگز:** رده پایین‌تر از حداقل تیم. مدل در cooldown. مدل منسوخ‌شده. درگاهی که کلیدش خراب است.

### مثال واقعی

تیم dev با `gemini-3.8-flash` روی کلید «gemini» خطای 429 گرفت:
1. سطح ۱: `gemini-2.5-pro` روی همان کلید گمینای (رده S) ← اگر سالم بود تمام.
2. سطح ۲: `gemini-3.8-flash` روی کلید «gemini 2» (کلید دیگر، سهمیه جدا).
3. سطح ۳: `deepseek-v4` روی reformboss (رده S).
4. سطح ۴: لازم نیست چون S بالاترین رده است.

## ۶. طبقه‌بندی خطاها و cooldown

هر نتیجه ناموفق در حافظه سلامت ثبت می‌شود (`llm_model_health`، توسعه‌یافته):

| خطا | تشخیص | cooldown مدل | cooldown درگاه/کلید |
|---|---|---|---|
| 429 | ریت‌لیمیت موقت مدل | ۶۰ ثانیه، بعد نمایی تا ۱۵ دقیقه | نه |
| 429 سه بار در ۵ دقیقه روی یک کلید | سهمیه کلید تمام شده | - | ۳۰ دقیقه برای کل کلید |
| 401 / 403 | کلید نامعتبر یا باطل‌شده | - | دائم، تا مدیر اصلاح کند + هشدار تلگرام |
| 404 روی مدل | مدل منسوخ‌شده | دائم (تا تازه‌سازی `/models`) | نه |
| 503 | سرویس خوابیده | ۵ دقیقه | ۵ دقیقه |
| تایم‌اوت / خطای شبکه | گذرا | بدون cooldown؛ فقط این فراخوانی رد می‌شود | نه |

موفقیت، شمارنده خطا را صفر و cooldown را پاک می‌کند.

## ۷. کشف پویای مدل‌ها

- هر درگاه هر ۱ ساعت فهرست `/models` را تازه می‌کند (کش در حافظه + settings).
- مدل تازه: رده‌بندی خودکار (بخش ۳.۳) + وضعیت اولیه «سالمِ تست‌نشده».
- مدلی که از فهرست حذف شده و 404 می‌دهد: «منسوخ» می‌شود و از چرخه خارج می‌ماند.
- مدیر در صفحه تنظیمات می‌تواند رده هر مدل را دستی بازنویسی کند؛ بازنویسی دستی بر قانون خودکار اولویت دارد.

## ۸. امبدینگ

امبدینگ امروز هیچ جایگزینی ندارد. معماری تازه:

- تنظیم اصلی `llm_embedding_model` می‌ماند (مدل ترجیحی).
- تنظیم تازه `llm_embedding_fallbacks`: فهرست مرتب `[{endpointId, model}]` که مدیر می‌چیند؛ پیش‌فرض از روی درگاه‌های موجود ساخته می‌شود.
- `getEmbedding` در `lib/rag.ts` به حلقه تبدیل می‌شود: اصلی ← جایگزین‌ها به ترتیب. همان جدول خطا و cooldown (بخش ۶) برای امبدینگ هم اعمال می‌شود.
- نکته فنی: بُعد بردار امبدینگ بین مدل‌ها فرق می‌کند. جایگزین فقط در همان فراخوانی استفاده می‌شود و در ایندکس ذخیره نمی‌شود، پس ناسازگاری بُعد پیش نمی‌آید. (اگر روزی خواستیم امبدینگ ذخیره‌شده را با مدل دیگر بازسازی کنیم، آن یک مهاجرت جداست.)

مدل‌های امبدینگ شناخته‌شده:
- `models/gemini-embedding-2-preview` (گمینای)
- `text-embedding-3-small` (سازگار با OpenAI)

## ۹. تنظیمات تازه (کلیدهای settings)

| کلید | ساختار | پیش‌فرض |
|---|---|---|

| `llm_team_min_tier` | `{ team: "S"\|"A"\|"B" }` | جدول بخش ۴ |
| `llm_endpoint_priority` | `[endpointId, ...]` | ترتیب فعلی درگاه‌ها |


## ۱۰. ماژول تازه: `lib/model-router.ts`

```typescript
export type ModelTier = 'S' | 'A' | 'B';

export interface RouteCandidate {
  endpointId: string;
  baseUrl: string;
  model: string;
  tier: ModelTier;
  level: 1 | 2 | 3 | 4;   // سطح زنجیره
}

/** رده یک مدل: اول بازنویسی دستی مدیر، بعد قانون خودکار. */
export function classifyTier(model: string, overrides?: Record<string, ModelTier>): ModelTier;

/** حداقل رده یک تیم. */
export function getTeamMinTier(team: TeamName): Promise<ModelTier>;

/** فهرست مرتب کاندیداها برای یک تیم (سطح ۱ تا ۴). */
export function routeChat(
  team: TeamName,
  opts?: { excludeEndpointId?: string; excludeModel?: string }
): Promise<RouteCandidate[]>;

/** فهرست مرتب کاندیداها برای امبدینگ. */
export function routeEmbedding(
  opts?: { excludeEndpointId?: string; excludeModel?: string }
): Promise<RouteCandidate[]>;

/** ثبت نتیجه برای حافظه سلامت. */
export function recordOutcome(
  endpointId: string, model: string,
  ok: boolean, status?: number, detail?: string
): Promise<void>;

/** آیا این جفت (درگاه، مدل) الان قابل استفاده است؟ */
export function isHealthy(endpointId: string, model: string): Promise<boolean>;

/** گروه‌بندی درگاه‌ها بر اساس ارائه‌دهنده (برای سطح ۲). */
export function groupByProvider(
  endpoints: LLMEndpoint[]
): Map<string, LLMEndpoint[]>;
```

تشخیص ارائه‌دهنده از روی `baseUrl`:
- شامل `generativelanguage.googleapis.com` ← `google`
- شامل `reformboss.com` ← `reformboss`
- بقیه ← هاستِ baseUrl

## ۱۱. تغییرات `callLLM` و `getEmbedding`

### `callLLM` (در `lib/llm.ts`)

```
۱. مدل اصلی تیم را مثل حالا resolve کن.
۲. امتحان کن.
۳. اگر موفق: recordOutcome(ok) و برگرد.
۴. اگر خطای قابل‌تلاش:
   الف. recordOutcome(fail, status)
   ب. candidates = routeChat(team, {excludeModel: مدل خراب})
   ج. برای هر کاندیدا به ترتیب:
      - اگر !isHealthy رد کن
      - امتحان کن؛ اگر موفق: recordOutcome(ok) و برگرد
      - اگر ناموفق: recordOutcome(fail) و ادامه
   د. اگر همه تمام شدند: خطای تجمیعی با فهرست کاندیداهای امتحان‌شده
۵. اگر خطای غیرقابل‌تلاش (مثل 400): مثل حالا مستقیم خطا بده.
```

نکته: پروب زنده («سلام» فرستادن) فقط وقتی انجام می‌شود که هیچ کاندیدای «سالمِ تست‌شده» در حافظه نباشد. در حالت عادی تصمیم روی حافظه سلامت است و تأخیر اضافه نداریم.

### `getEmbedding` (در `lib/rag.ts`)

```
۱. مدل اصلی امبدینگ را امتحان کن.
۲. اگر موفق برگرد.
۳. اگر خطا: recordOutcome و بعد routeEmbedding؛ به ترتیب امتحان کن.
۴. اگر همه خراب بودند: RAGError با پیام «هیچ درگاه امبدینگ سالمی نیست».
```

### قانون عدم تنزل دائمی

- `team_models` دست‌نخورده می‌ماند (مدل «ترجیحی»).
- جایگزینی فقط در همان فراخوانی است.
- استثنا (به‌روزرسانی ترجیحی)، فقط وقتی:
  - مدل ترجیحی `deprecated` شده (404 دائم)، یا
  - ۵ فراخوانی پیاپی به جایگزینی با رده مساوی یا بالاتر رسیده‌ایم.
- در این دو حالت، مدل ترجیحی تیم به‌روز می‌شود و در لاگ فارسی ثبت می‌شود.

جایگزینی `findWorkingModel` و `KNOWN_FALLBACK_MODELS` فعلی با روتر. `circuit breaker` فعلی داخل `recordOutcome` ادغام می‌شود (منطق ۳ خطا دیگر لازم نیست چون cooldown نمایی دقیق‌تر است).

## ۱۲. مانیتورینگ

- هر جایگزینی در لاگ با پیشوند `[model-router]` ثبت می‌شود: تیم، سطح، از چه مدلی به چه مدلی، دلیل.
- ویجت «سلامت مدل‌ها» در داشبورد: جدول درگاه × مدل با رنگ وضعیت و زمان پایان cooldown.
- هشدار تلگرام فقط برای دو حالت: کلید مرده (401/403) و «هیچ کاندیدای سالمی برای تیم X نیست».
- آمار: شمارش جایگزینی موفق به تفکیک سطح، برای اینکه بفهمیم کدام سطح بیشتر به کار می‌آید.

## ۱۳. نقشه پیاده‌سازی

| قدم | کار | خروجی |
|---|---|---|
| ۱ | `lib/model-router.ts`: رده‌بندی، گروه‌بندی ارائه‌دهنده، حافظه سلامت | ماژول تازه |
| ۲ | `recordOutcome` + `isHealthy` + توسعه `llm_model_health` | سلامت متمرکز |
| ۳ | `routeChat` با ۴ سطح | زنجیره چت |
| ۴ | بازنویسی fallback در `callLLM` با روتر؛ حذف `KNOWN_FALLBACK_MODELS` | چت هوشمند |
| ۵ | `routeEmbedding` + حلقه در `getEmbedding` | امبدینگ هوشمند |
| ۶ | تنظیمات داشبورد: رده مدل‌ها، حداقل رده تیم، اولویت درگاه، جایگزین‌های امبدینگ | UI مدیریت |
| ۷ | ویجت سلامت مدل‌ها + هشدار تلگرام | دید |
