# معماری ساب‌ایجنت دانش

سند طراحی ـ تیم ۱ از ۱۰ تیم مدیریت دانش تایلندگرد
تاریخ: ۲۳ مهر ۱۴۰۵

---

## ۱. مسئله

هر ۱۵ تیم تایلندگرد امروز دو مسیر یادگیری دارند: حافظهٔ چرخه (`team_memory`) و دانش RAG
(`team_knowledge` + `knowledge_chunks`). ولی هیچ‌کدام «فعال» نیستند؛ یعنی هیچ جزئی
در چرخه نیست که سراغ منابع بیرونی معتبر برود، چیز تازه بخواند و به دانش تیم اضافه کند.
دانش فقط وقتی رشد می‌کند که کسی دستی چیزی ثبت کند یا منتقد حکمی بدهد.

ساب‌ایجنت دانش این خلأ را پر می‌کند: یک مرحلهٔ رسمی، قابل‌مشاهده و قابل‌اندازه‌گیری
در ابتدای نوبت هر تیم که «یادگیری بیرونی» را انجام می‌دهد.

---

## ۲. جایگاه در چرخه اجرا

### تصمیم: قبل از سرپرست، به‌صورت ترتیبی، در سطح ارکستراتور

```
runSingleTeam (lib/orchestrator.ts)
 ├─ reportProgress('شروع اجرا', ۵)            ← شبه‌وظیفه، ردیف ساب‌ایجنت نمی‌سازد
 ├─ ★ runKnowledgeSubagent(team, ...)         ← ساب‌ایجنت دانش (جدید)
 │    └─ reportProgress('دانش: گردآوری', ۸)  ← ردیف ساب‌ایجنت می‌سازد
 ├─ loadRunTeam / loadTeamMemory / ...
 └─ runTeam(input)                            ← سرپرست ← مجری‌ها ← منتقد
      ├─ reportProgress('سرپرست: ...', ۱۵)    ← ردیف «دانش» خودکار موفق بسته می‌شود
      └─ ...
```

**چرا ترتیبی و قبل از سرپرست، نه موازی؟**
سرپرست در همین چرخه از دانش در پرامپتش استفاده می‌کند
(`buildKnowledgePromptSection` در ابتدای زمینه تزریق می‌شود).
اگر گردآوری دانش موازی با سرپرست اجرا شود، دانش تازه یک چرخه دیر می‌رسد و حلقهٔ
«یاد بگیر ← برنامه بریز ← اجرا کن» می‌شکند.
هزینهٔ ترتیبی بودن: در حالت به‌روزرسانی حداکثر حدود ۱ تا ۲ دقیقه، در حالت رد
(دانش تازه است) فقط ۱ تا ۲ ثانیه کوئری دیتابیس بدون هیچ فراخوانی LLM.

**چرا در سطح ارکستراتور، نه داخل هر فایل تیم؟**
با یک نقطهٔ اتصال در `runSingleTeam` هر ۱۵ تیم ــ و هر تیم آینده ــ خودکار صاحب
ساب‌ایجنت دانش می‌شوند؛ بدون ویرایش ۱۵ فایل. «هر تیم یک ساب‌ایجنت دارد» از نظر
منطقی برقرار است (ردیف جدا در جدول `subagents` با ستون `team`) و از نظر فیزیکی
کد مشترک در یک ماژول `lib/knowledge-subagent.ts` زندگی می‌کند.
تخصیص تیمی از دو جا می‌آید: مأموریت تیم از `TEAM_META` و فهرست منابع از جدول
`knowledge_sources` (بخش ۶).

## ۳. ورودی ساب‌ایجنت

```typescript
interface KnowledgeSubagentInput {
  team: TeamName;                    // کدام تیم
  runId: string;                     // شناسهٔ چرخه (برای لاگ و تاریخچه)
  ragContext: string;                // زمینهٔ این چرخه (برای سنجش ربط)
  reportProgress: ProgressReporter;  // همان گزارش‌دهندهٔ ارکستراتور
}
```

ساب‌ایجنت خودش این‌ها را از دیتابیس می‌خواند (بدون LLM):

- مأموریت تیم از `TEAM_META[team].mission`
- فهرست منابع فعال تیم از `knowledge_sources` (بخش ۶)، مرتب بر اساس
  قدیمی‌ترین `last_checked_at` (چرخش منابع)
- موجودی دانش فعلی: عنوان و تاریخ آخرین دانش‌های تیم از `team_knowledge`
  (فقط برای تصمیم تازگی؛ متن کامل خوانده نمی‌شود)

**قانون تازگی (بدون هزینهٔ LLM):**
اگر همهٔ منابع فعال تیم در `refresh_interval` چرخهٔ اخیر بررسی شده باشند،
ساب‌ایجنت اصلاً سراغ فچ و LLM نمی‌رود (بخش ۵، حالت رد).
پیش‌فرض `refresh_interval = ۲` چرخه، قابل تنظیم برای هر تیم.

## ۴. خروجی ساب‌ایجنت

```typescript
interface NewKnowledgeItem {
  title: string;                 // عنوان کوتاه فارسی
  content: string;               // ۲ تا ۵ جملهٔ فارسی، کاربردی، بدون کلی‌گویی
  sourceName: string;            // نام منبع (نمایشی)
  sourceUrl: string;             // آدرس دقیق صفحه‌ای که خوانده شد
  authorityTier: 1 | 2 | 3;      // درجهٔ اعتبار منبع
  category?: string;             // نام دسته (اگر برای تیم دسته تعریف شده)
  relevantTeams?: TeamName[];    // قلاب فاز ۲: اشتراک بین‌تیمی
}

interface KnowledgeSubagentResult {
  refreshed: boolean;            // آیا به‌روزرسانی واقعی انجام شد؟
  sourcesChecked: string[];      // نام منابعی که در این نوبت بررسی شدند
  newItems: NewKnowledgeItem[];  // یافته‌های تازه (خالی اگر چیزی نبود)
  skippedReason: string | null;   // دلیل رد/عدم‌یافت، فارسی و کوتاه
  summary: string;                // یک خط فارسی برای لاگ و تاریخچه
  llmCalls: number;               // تعداد فراخوانی‌های LLM این مرحله
}
```

**دو کانال اثرگذاری خروجی:**

1. **ماندگار:** هر آیتم در `team_knowledge` با `source = 'knowledge-subagent'`
   درج و با `indexKnowledge` ایندکس می‌شود؛ پس سرپرست همین چرخه از طریق
   `buildKnowledgePromptSection` آن را می‌بیند و چرخه‌های بعد هم دارند.
2. **فوری:** خلاصهٔ یافته‌های تازه (حداکثر ۳ خط) به ابتدای `ragContext` تیم
   الصاق می‌شود با سربرگ «یافته‌های تازهٔ دانش این چرخه»؛ حتی اگر ایندکس
   امبدینگ لحظه‌ای خطا بدهد، سرپرست از یافته‌ها بی‌نصیب نمی‌ماند.

## ۵. سه حالت پایانی (مهم‌ترین تصمیم رفتاری)

| حالت | شرط | رفتار |
|---|---|---|
| به‌روزرسانی شد | حداقل یک آیتم تازهٔ غیرتکراری | درج + ایندکس + تزریق در زمینه؛ ردیف ساب‌ایجنت موفق |
| رد سالم | دانش تازه است یا منبعی ثبت نشده | هیچ فچ/LLM؛ `refreshed=false` با `skippedReason` فارسی؛ ردیف ساب‌ایجنت **موفق** |
| چیز تازه‌ای نبود | منابع خوانده شدند ولی نکتهٔ نو/مرتبطی نداشتند | `refreshed=false`؛ ردیف ساب‌ایجنت موفق؛ `empty_streak` منبع +۱ |

**«پیدا نکردن» خطا نیست.** ساب‌ایجنت دانش مثل نگهبان است؛ شبی که دزدی نیست،
گزارشش «همه‌چیز امن بود» است نه «شکست». داشبورد باید سه وضعیت را جدا نشان بدهد:
«به‌روزرسانی شد» / «به‌روز است» / «خطا». فقط حالت سوم نیازمند توجه است.

**خطا (حالت چهارم، نادر):** هر خطایی در فچ، LLM یا ایندکس، fail-soft است
(الگو: `lib/market.ts`). زنجیرهٔ تحمل:
فچ منبع زنده (تایم‌اوت ۱۵ ثانیه، حداکثر ۲ منبع در هر نوبت) ←
خطا در یک منبع، منبع بعدی را متوقف نمی‌کند ←
خطای LLM در استخراج، کل مرحله را fail نمی‌کند ←
خطای `indexKnowledge`، ردیف `team_knowledge` را نگه می‌دارد (ایندکس مجدد بعدی)
و یافته از کانال فوری (بخش ۴) به سرپرست می‌رسد.
در هیچ حالتی تیم متوقف نمی‌شود؛ حداکثر با دانش قبلی جلو می‌رود.

## ۶. جدول منابع دانش (`knowledge_sources`)

```sql
knowledge_sources (
  id               uuid primary key,
  team             text not null,            -- یکی از ۱۵ تیم
  name             text not null,            -- نام نمایشی منبع
  url              text not null,            -- آدرس صفحه/فید
  source_type      text default 'article',   -- article | docs | rss (فاز ۱: article/docs)
  authority_tier   smallint default 3,       -- ۱: سند رسمی/استاندارد، ۲: نشریهٔ متخصص، ۳: تجربهٔ کاربردی
  is_active        boolean default true,
  last_checked_at  timestamptz,              -- برای چرخش منابع
  empty_streak     smallint default 0,       -- چند نوبت پیاپی چیز تازه‌ای نداشت
  created_at       timestamptz default now()
)
```

- بذر اولیهٔ هر تیم (۲ تا ۳ منبع معتبر) در کد به‌صورت پیش‌فرض می‌آید؛
  مدیر از داشبورد (کار تیم دیگر) می‌تواند اضافه/حذف/فعال/غیرفعال کند.
- چرخش: هر نوبت حداکثر ۲ منبع با قدیمی‌ترین `last_checked_at` انتخاب می‌شوند.
- اگر `empty_streak` منبعی به ۳ رسید، در اولویت چرخش می‌افتد و در داشبورد
  برای جایگزینی پرچم می‌خورد.
- امنیت: فقط `http/https`، سقف ۲ مگابایت پاسخ، تایم‌اوت ۱۵ ثانیه.
  آدرس‌ها را مدیر ثبت می‌کند (ورودی کاربر آزاد نیست).

## ۷. خط لولهٔ داخلی (حداکثر ۲ فراخوانی LLM در حالت به‌روزرسانی)

```
۱. انتخاب منبع (بدون LLM)
   └─ ۲ منبع فعال با قدیمی‌ترین last_checked_at

۲. فچ و تمیزکاری (بدون LLM)
   └─ دریافت HTML ← استخراج متن (حذف تگ/اسکریپت/استایل) ← برش ۸ هزار کاراکتر اول

۳. استخراج نکته (۱ فراخوانی LLM، JSON)
   ورودی: مأموریت تیم + متن تمیزشده + درجهٔ اعتبار منبع
   خروجی: حداکثر ۳ آیتم {title, content} یا آرایهٔ خالی
   قانون پرامپت: «فقط نکتهٔ مشخص و کاربردی؛ اگر چیز تازه و مرتبطی نیست،
   آرایهٔ خالی برگردان. کلی‌گویی ممنوع.»

۴. تکراری‌زدایی (بدون LLM)
   └─ برای هر آیتم: retrieveKnowledge(عنوان) روی همین تیم؛
      اگر نزدیک‌ترین چانک به‌وضوح همان نکته است → رد

۵. ذخیره (بدون LLM)
   ├─ درج در team_knowledge (source='knowledge-subagent')
   ├─ indexKnowledge (fail-soft؛ ردیف والد می‌ماند)
   ├─ درج در knowledge_history با action='external-refresh' و خلاصه
   └─ به‌روزرسانی last_checked_at و empty_streak منبع
```

سقف مصرف هر تیم در هر چرخه: ۲ فچ + حداکثر ۲ فراخوانی LLM (یکی برای هر منبع).
در حالت رد: صفر فراخوانی.

## ۸. ثبت در جدول `subagents`

از سازوکار موجود ارکستراتور استفاده می‌شود؛ کد جدیدی برای ردیف لازم نیست:

- شروع مرحله: `reportProgress('دانش: گردآوری', ۸)` → ردیف با
  `label='دانش: گردآوری'`، `status='running'`، `team` و `team_run_id` ساخته می‌شود.
- پایان: وقتی تیم اولین `reportProgress` بعدی را می‌زند (مثلاً «سرپرست: …»)،
  سازوکار فعلی ارکستراتور ردیف‌های `running` قبلی را `success` می‌کند.
  پس ردیف دانش خودکار با `finished_at` بسته می‌شود و `started_at → finished_at`
  همان «مدت گردآوری دانش» است که در داشبورد دیده می‌شود.
- برچسب ثابت «دانش: گردآوری» در همهٔ تیم‌ها عمدی است تا داشبورد بتواند
  مرحلهٔ دانش را جدا فیلتر و مقایسه کند.
- جزئیات نتیجه (چند آیتم تازه / دلیل رد) در `knowledge_history` و لاگ ورکر
  ثبت می‌شود (بخش ۵)؛ ستون تازه‌ای لازم نیست.

کنترل کاربر (توقف/ادامه) روی این مرحله هم مثل بقیهٔ مراحل از همان مسیر
`enforceControl` اعمال می‌شود؛ رفتار جدیدی تعریف نمی‌شود.

## ۹. نسبت با مسیرهای یادگیری موجود

| مسیر | جهت | محرک | وضعیت |
|---|---|---|---|
| ساب‌ایجنت دانش (این سند) | بیرونی → درونی | هر نوبت تیم، منابع معتبر | جدید |
| نقد ← دانش (الگوی برندینگ) | درونی (خطای خودمان) | حکم منتقد هر چرخه | موجود در برندینگ؛ تعمیم به ۱۵ تیم با تیم دیگر |
| حافظهٔ چرخه (`team_memory`) | درونی | `remember(runId, lesson)` | موجود، دست نمی‌خورد |
| مربی دانش (`lib/teams/knowledge.ts`) | نظارتی | صفحه/API داشبورد | موجود؛ بازوی اجرایی‌اش همین ساب‌ایجنت است |

هر سه مسیر نوشتن در یک مخزن (`team_knowledge`) می‌ریزند و فقط در ستون `source`
از هم جدا می‌شوند: `'knowledge-subagent'` در برابر `'team-lesson'` در برابر
`'manager'`. خواندن (RAG) برای هر سه یکسان است؛ پس دانشِ از-خطا و دانشِ از-منبع
در پرامپت سرپرست کنار هم می‌نشینند.

## ۱۰. قراردادهای مشترک برای ۹ تیم دیگر

برای اینکه کار موازی قفل نشود، این قراردادها ثابت‌اند و تیم‌های دیگر روی آن‌ها
می‌سازند:

1. نام ماژول مشترک: `lib/knowledge-subagent.ts` با تابع
   `runKnowledgeSubagent(team, input)` و اینترفیس‌های بخش ۴.
2. برچسب ردیف ساب‌ایجنت: دقیقاً «دانش: گردآوری» (بدون تغییر، بدون پسوند تیم).
3. مقدار `source` در `team_knowledge` برای این مسیر: دقیقاً `'knowledge-subagent'`.
4. اکشن تاریخچه در `knowledge_history`: `'external-refresh'` (موفق/رد) و
   `'external-refresh-failed'` (خطای غیرمنتظره، نادر).
5. جدول `knowledge_sources` با ستون‌های بخش ۶؛ تیم منابع مسئول بذر اولیه است،
   تیم UI مسئول صفحهٔ مدیریت.
6. هیچ تیمی `runKnowledgeSubagent` را مستقیم صدا نمی‌زند؛ فقط ارکستراتور.
   اگر تیمی نیاز خاص داشت (مثلاً اینتل که خودش فچ دارد)، از طریق منابع
   ثبت‌شده در `knowledge_sources` اعمال می‌شود، نه کد جدا.

## ۱۱. ریسک‌ها و تصمیم‌های آگاهانه

- **هزینه:** سقف ۲ LLM در هر تیمِ نیازمند به‌روزرسانی؛ با قانون تازگی،
  بیشتر نوبت‌ها صفر هزینه‌اند. اگر صورت‌حساب بالا رفت، `refresh_interval`
  از تنظیمات کم‌ریسک‌ترین پیچ است.
- **کیفیت منبع:** درجهٔ اعتبار در فاز ۱ فقط نمایشی/مدیریتی است؛
  اثر مکانیکی (وزن‌دهی در بازیابی) به فاز ۲ موکول شده تا اول دیتا جمع شود.
- **تاخیر چرخه:** بدترین حالت +۲ دقیقه برای یک تیم؛ چون ورکر گیت‌هاب
  تیم‌ها را تک‌تک جلو می‌برد، اثر تجمعی روی کل چرخه حداکثر همین است.
- **وابستگی به فچ:** اگر سایتی ساختارش را عوض کند، استخراج متن ساده ممکن است
  خروجی بی‌کیفیت بدهد؛ پرامپت استخراج موظف است در این حالت آرایهٔ خالی برگرداند
  (نه حدس زدن)، و `empty_streak` منبع را بالا می‌برد تا جایگزین شود.

## ۱۲. معیار پذیرش (کی بگوییم درست کار می‌کند)

1. در هر چرخه، هر ۱۵ تیم دقیقاً یک ردیف «دانش: گردآوری» با وضعیت نهایی
   مشخص دارند (بدون ردیف گیرکرده).
2. حداقل ۸۰٪ نوبت‌ها در حالت «رد سالم» یا «چیز تازه‌ای نبود» تمام می‌شوند
   (نشانهٔ کارکرد قانون تازگی، نه تنبلی).
3. دانش‌های با `source='knowledge-subagent'` در بازیابی RAG سرپرست همان تیم
   دیده می‌شوند (تست: کوئری عنوان آیتم تازه).
4. هیچ چرخه‌ای به‌خاطر خطای این مرحله متوقف/ناموفق نشده است (fail-soft).
