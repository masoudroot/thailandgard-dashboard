# ماشین حالت چرخهٔ تایلندگرد
## Cycle State Machine

**نسخه:** ۱.۰
**تاریخ:** ۲۳ مهر ۱۴۰۵
**مبنا:** کد واقعی `lib/orchestrator.ts`، `worker/cycle-worker.ts`، `lib/types.ts` و اسکیمای دیتابیس

---

## ۱. نقشهٔ کلی

چرخه سه لایهٔ حالت دارد که روی هم سوارند:

```
چرخه (cycles)            یک ردیف در هر چرخه
  └─ موج (مشتق‌شده)      ۶ موج ثابت، بدون ردیف دیتابیس؛ از team_runs استنتاج می‌شود
       └─ تیم (team_runs) یک ردیف در هر اجرای تیم
            └─ ساب‌ایجنت (subagents) یک ردیف در هر مرحلهٔ تیم
```

دو موتور اجرا وجود دارد که **نباید هم‌زمان** کار کنند:

| موتور | فایل | مدل اجرا |
|---|---|---|
| ورکر گیت‌هاب | `worker/cycle-worker.ts` | هر اجرا فقط **یک تیم**، کرون هر ۵ دقیقه |
| API ورسل (قدیمی) | `runAllWaves` در ارکستراتور | همهٔ موج‌ها در یک فرایند، موازی با سقف ۳ |

تصمیم معماری: فقط ورکر گیت‌هاب موتور است. مسیر `runAllWaves` از API نباید صدا زده شود.

## ۲. حالت‌های چرخه (cycles.status)

```
                  ┌─────────────────────────────────────────────┐
                  │                                             ▼
(وجود ندارد) ──► running ──► pausing ──► paused ──► running ──► success
                  │             │            │                     ▲
                  │             │            └────► canceled ──────┘
                  │             └─────────────────► canceled
                  └──────────────────────────────► failed
                                                   canceled
```

حالت‌های پایانی: `success` ،`failed` ،`canceled` (دیگر برنمی‌گردند).
حالت‌های فعال: `running` ،`pausing` ،`paused` (ثابت `ACTIVE_CYCLE_STATUSES`).

### جدول گذارها

| از | به | رویداد | چه کسی انجام می‌دهد |
|---|---|---|---|
| (وجود ندارد) | running | شروع چرخه | `beginCycle()`؛ از API (`POST /api/manager/cycle/start`) یا ورکر (`start-cycle`) |
| running | pausing | درخواست توقف نرم | `requestPause()`؛ کاربر از داشبورد |
| pausing | paused | پایان موج جاری | `checkpointBeforeWave()`؛ حلقهٔ اجرا بین موج‌ها |
| paused | running | ادامه | `resumeCycle()`؛ کاربر از داشبورد |
| paused | canceled | لغو در حالت توقف | `cancelCycle()`؛ کاربر از داشبورد |
| running/pausing | canceled | لغو | `cancelCycle()`؛ کاربر از داشبورد |
| running | success | همهٔ تیم‌ها موفق | `finishCycle()`؛ ارکستراتور یا ورکر |
| running | failed | خطای مرگبار یا تیم ناموفق | `finishCycle()`؛ ارکستراتور یا ورکر |

### نکات مهم

۱. گذار `pausing` به `paused` **داخل فرایند در حال اجرا** رخ می‌دهد، نه اتمیک در دیتابیس. اگر فرایند بین این دو بمیرد، چرخه در `pausing` می‌ماند.
۲. در حالت `paused` حلقهٔ اجرا هر ۵ ثانیه قفل را لمس می‌کند تا زنده بماند (`touchPausedLock`).
۳. `resumeCycle` اگر حلقهٔ درون‌حافظه‌ای مرده باشد، `resumeRemainingWaves` را در پس‌زمینه اجرا می‌کند.
۴. `finishCycle` آمار را در `stats` می‌نویسد: تعداد تیم‌ها، موفق/ناموفق، مجموع `llm_calls`، مدت به دقیقه.

## ۳. حالت‌های تیم (team_runs.status)

```
(ردیف وجود ندارد) = pending ──► running ──► success
                                       ├─► failed
                                       └─► stopped
```

نوع `TeamRunStatus` شش مقدار دارد: `pending` ،`running` ،`success` ،`failed` ،`skipped` ،`stopped`.

### جدول گذارها

| از | به | رویداد | چه کسی انجام می‌دهد |
|---|---|---|---|
| pending (ضمنی) | running | شروع اجرای تیم | `runSingleTeam()`؛ درج ردیف با `status='running'` |
| running | success | خروجی تأیید شد | `runSingleTeam()`؛ وقتی `result.approved !== false` |
| running | failed | خطا یا رد منتقد | `runSingleTeam()`؛ وقتی `result.approved === false` یا exception |
| running | failed | تایم‌اوت ۱۵ دقیقه | فقط ورکر گیت‌هاب؛ بر اساس `started_at` |
| running | stopped | توقف توسط کاربر | `runSingleTeam()`؛ وقتی ساب‌ایجنت `SubagentStoppedError` بدهد |

### نکات مهم

۱. **`pending` هیچ‌وقت در دیتابیس نوشته نمی‌شود.** نبودن ردیف یعنی معلق بودن. ورکر با `teamStatus[t] ?? 'pending'` همین را فرض می‌کند.
۲. **`skipped` هیچ‌وقت نوشته نمی‌شود.** در `resumeRemainingWaves` فقط یک `Set` درون‌حافظه‌ای است.
۳. **ستون `retry_of` وجود دارد ولی هیچ‌کس آن را پر نمی‌کند.** بازاجرای خودکار تیم ناموفق پیاده نشده است؛ تیم `failed` یعنی پایان آن تیم در این چرخه.
۴. وضعیت نهایی تیم از `result.approved` تعیین می‌شود، نه فقط از exception (اصلاح باگ «موفق دروغین»).
۵. `progress` و `current_task` زنده به‌روز می‌شوند؛ ضربان هر ۶۰ ثانیه ردیف را لمس می‌کند.

## ۴. موج‌ها (۶ موج ثابت)

موج ردیف دیتابیس ندارد؛ از `WAVES` در `lib/types.ts` و ستون `wave` در `team_runs` استنتاج می‌شود:

| موج | تیم‌ها |
|---|---|
| ۱ | artdir ،branding ،content |
| ۲ | analytics ،intel ،lead |
| ۳ | design ،seo ،seocontent |
| ۴ | design-ir ،dev ،farsiui |
| ۵ | vibefarsi ،qa |
| ۶ | inspector |

### قوانین پیشروی

- **حالت ورکر (فعلی):** هر اجرای ورکر فقط **یک تیم** را اجرا می‌کند. موج جاری = اولین موجی که همهٔ تیم‌هایش تمام نشده‌اند. اگر تیمی از موج جاری `running` باشد، ورکر صبر می‌کند و خارج می‌شود.
- **حالت API (قدیمی):** تیم‌های یک موج موازی با سقف ۳ هم‌زمان (`WAVE_CONCURRENCY = 3`)، موج‌ها پشت سر هم.
- موج بعدی فقط وقتی شروع می‌شود که همهٔ تیم‌های موج جاری به یکی از حالت‌های `success` ،`failed` ،`stopped` رسیده باشند.
- چرخه وقتی بسته می‌شود که هر ۱۵ تیم در یکی از این سه حالت باشند (ورکر: `allDone`).

## ۵. قفل سراسری (agent_state)

کلید `orchestrator:lock` در جدول `agent_state`، از جنس JSON:

```json
{
  "status": "running",
  "run_id": "run-20261015142430-q4fd7w",
  "cycle_id": "uuid",
  "started_at": "2026-10-15T14:24:30Z"
}
```

| قانون | مقدار | محل |
|---|---|---|
| قفل تازه یعنی «چرخهٔ دیگری در حال اجراست» | جوان‌تر از ۱۵۰ دقیقه | `LOCK_TTL_MINUTES` |
| شروع چرخهٔ جدید با قفل تازه | خطای `CycleLockedError` | `acquireLock()` |
| حلقهٔ توقف، قفل را زنده نگه می‌دارد | هر ۵ ثانیه | `touchPausedLock()` |
| حلقهٔ توقف زنده حساب می‌شود اگر | قفل جوان‌تر از ۱۰ دقیقه باشد | `PAUSE_LOOP_ALIVE_MS` |

### شکاف شناخته‌شده

ورکر گیت‌هاب قفل را فقط در `beginCycle` می‌نویسد و در `finishCycle` آزاد می‌کند؛ بین این دو، لمس دوره‌ای ندارد. اگر چرخه‌ای بیش از ۱۵۰ دقیقه طول بکشد (۱۵ تیم با فاصلهٔ ۵ دقیقه‌ای = حداقل ۷۵ دقیقه به‌علاوهٔ تأخیر LLM)، قفل کهنه حساب می‌شود و یک `start-cycle` جدید می‌تواند وسط چرخهٔ فعال، چرخهٔ تازه بسازد. **راه‌حل پیشنهادی:** ورکر در هر اجرا قفل را لمس کند، یا `LOCK_TTL_MINUTES` بر اساس حالت ورکر بیشتر شود.

## ۶. حالت‌های ساب‌ایجنت (subagents.status)

```
pending ──► running ──► paused ──► running ──► success
                │           │                    ▲
                │           └────► stopped ───────┘
                └────────────────► failed
```

سیگنال کنترلی (`control`): `run` ،`pause` ،`stop`. کاربر از داشبورد می‌فرستد؛ ارکستراتور در **مرز مرحله‌ها** اعمال می‌کند (روی مرحلهٔ در حال اجرا اثر ندارد). مهلت انتظار برای ادامه: ۳۰ دقیقه (`PAUSE_TIMEOUT_MS`)، بعد از آن `stopped`.

## ۷. ستون‌های موردنیاز دیتابیس

### جدول cycles (فعلی: کافی است)

| ستون | نوع | کاربرد در مدل |
|---|---|---|
| id | uuid | کلید اصلی |
| run_id | text | شناسهٔ خوانای چرخه (`run-YYYYMMDDHHMMSS-xxxxxx`) |
| status | text | حالت چرخه (۶ مقدار بخش ۲) |

| finished_at | timestamptz | پایان (فقط حالت‌های پایانی) |

**پیشنهاد افزودنی:**

| team | text | نام تیم |

| output_summary | text | خلاصهٔ خروجی (سقف ۴۰۰۰ کاراکتر) |

## ۸. چه کسی چه گذاری را انجام می‌دهد (خلاصه)

| عامل | مسئولیت در مدل حالت |
|---|---|
| ورکر گیت‌هاب (`cycle-worker.ts`) | شروع چرخه (`start-cycle`)؛ اجرای یک تیم در هر اجرا؛ تایم‌اوت تیم گیرکرده؛ بستن چرخه وقتی همه تمام شدند |
| ارکستراتور (`lib/orchestrator.ts`) | درج و به‌روزرسانی `team_runs`؛ مدیریت ساب‌ایجنت‌ها؛ قفل؛ توقف/ادامه/لغو؛ آمار نهایی |
| کاربر (داشبورد) | فقط سه گذار: `requestPause` ،`resumeCycle` ،`cancelCycle` |
| کرون ورسل (`/api/cron/cycle-tick`) | **باید حذف شود**؛ متعلق به معماری قدیمی است و با ورکر تداخل می‌کند |

## ۹. شکاف‌های مدل فعلی (برای تیم‌های اجرایی)

۱. **تایم‌اوت ۱۵ دقیقه‌ای ورکر** بر اساس `started_at` است، نه ضربان واقعی. تیم سالمِ کند کشته می‌شود. باید ضربان (`updated_at`) و مرحلهٔ فعال مبنا باشد.
۲. **`retry_of` بلامصرف است.** بازاجرای خودکار تیم ناموفق وجود ندارد؛ خواست مسعود این است که خطا با تعویض مدل و اجرای دوباره همان تیم درمان شود، نه اینکه تیم `failed` بماند.
۳. **قفل در حالت ورکر لمس نمی‌شود** (بخش ۵). ریسک ساخت چرخهٔ دوم روی چرخهٔ فعال پس از ۱۵۰ دقیقه.
۴. **ورکر `previousWavesOutput: {}` می‌فرستد.** زمینهٔ موج‌های قبلی به تیم بعدی نمی‌رسد.
۵. **`pending` و `skipped` هیچ‌وقت در دیتابیس ثبت نمی‌شوند.** داشبورد باید «نبودن ردیف» را معلق تفسیر کند؛ قرارداد شکننده است.
۶. **دو موتور هم‌زمان فعال‌اند** (ورکر + کرون ورسل). تا کرون ورسل از `vercel.json` حذف نشود، تداخل ادامه دارد.
۷. **زمان‌بندی گیت‌هاب (`schedule`) تضمینی نیست.** اگر کرون ۵ دقیقه‌ای شلیک نشود، چرخه می‌ایستد و هیچ نگهبانی آن را بیدار نمی‌کند. پیشنهاد: نگهبان خارجی (همین واچ‌داگ) چرخهٔ `running` بدون پیشرفت بیش از ۱۵ دقیقه را تشخیص دهد و هشدار دهد.
